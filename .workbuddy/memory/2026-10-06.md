- **依赖变化**：LangChain 1.x 已移除 `langchain.document_loaders`，官方 Loader 现在在
  `langchain-community` 里。已安装 `langchain-community==0.4.2` + `docx2txt==0.9`
  （连带 langchain-classic 1.0.8、SQLAlchemy 2.1.3），requirements.txt 已同步。
- Loader 映射：PyPDFLoader / TextLoader / Docx2txtLoader，通过 `LOADER_REGISTRY` 按扩展名分发。
- 定制点：① 中文分隔符序列（LangChain 默认分隔符对中文不友好）；② `_detect_encoding()`
  按 utf-8 → utf-8-sig → gb18030 → big5 顺序探测编码，解决中文 Windows 的 GBK 文件；

  原因是 splitter 只按分隔符边界回退，不会为凑满 overlap 而切断完整句子。这是预期行为，已写入 README。

## 重排序优化 + 逐段溯源（Agent 应用场景 #17 续）

- 需求：用百炼 `gte-rerank` 对初次检索结果二次重排提升 Top-1 准确率；回答每段末尾标注引用自哪个文件的对应片段。
- **新增 `src/reranker.py`**：`DashScopeReranker` 封装 dashscope `TextReRank.call`
  （`return_documents=False` 省 token、`top_n` 截断）。三条健壮性设计：
  ① **模型自动回退** —— 实测 `gte-rerank` 在本账号返回 `403 Access denied`（需在控制台开通），
     自动切到备用模型 `gte-rerank-v2`（返回 200）并记住可用模型，后续不再重试失败模型；
  ② **失败降级** —— 排序异常不抛错，返回粗排顺序（`rerank_score=None`），问答链路不受影响；
  ③ 空白片段不参与打分但下标严格对齐。`active_model` 表示实际生效的模型名。
- **新增 `src/citations.py`**：把「模型给的 `[n]` 编号」机械映射成真实文件名/页码。
  `split_paragraphs` / `extract_markers` / `strip_markers` / `build_segments` / `format_citation_tag` /
  `annotate_answer`（每段末尾追加 `【来源：员工手册.pdf（第 2 页）】`，与正文之间用空行隔开）/
  `annotate_partial`（流式只标注已写完的段落，末段保持原样）。
  关键原则：**编号→文件由系统映射，模型无法伪造来源**；编号对不上就不标（宁缺毋滥）。
- **`src/kb.py` 改造**：`search_from_db` 支持 `rerank` / `recall_k` 两阶段检索
  （粗排 `max(TOP_K×3, 10)` 条候选 → 阈值过滤 → 精排 → Top-K）；命中结构统一补齐
  `vector_score / rerank_score / rerank_model / recall_rank / recall_total`（未重排时为 None，
  界面无需分支处理）。`kb_chat` / `kb_chat_stream` 透传参数并新增返回
  `answer_annotated / segments / retrieval{rerank, rerank_model, candidates, returned}`；
  抽了 `_empty_result()` 与 `_retrieval_info()` 保证兜底返回字段一致。
  候选数不超过 Top-K 时跳过重排（省一次调用）；阈值作用在向量粗排余弦上。
- **提示词强化**：要求每段末尾标注片段编号（`[1]`/`[1][3]`）、段落之间空行分隔、禁止使用不存在的编号。
- **`config.py`**：`_env_bool` / `_env_list` 两个解析器；新增 `RERANK_ENABLED=true`、
  `RERANK_MODEL=gte-rerank`、`RERANK_FALLBACK_MODELS=gte-rerank-v2`、`RERANK_RECALL_K=0`（0=自动）、

- 用户手动删除了旧 release，希望把改版后的内容作为 v0.1.0 重新发布。
- **重要认知：删除 GitHub release 不一定删除 tag**。本次排查发现 release 已删但
  `refs/tags/v0.1.0` 仍在（指向旧提交 `7b25b63`）。用 `gh api repos/<owner>/<repo>/git/refs/tags`
  查 tag 列表，比 `git ls-remote` 更稳（后者在本机代理下经常 502）。
- 做法：`git tag -f v0.1.0 <最新提交>` 挪本地 tag → 删远程旧 tag → 在最新提交上重新发。
- **踩坑**：这台机器的网络代理（`127.0.0.1:50891`）极不稳定，`git push` / `gh api` 会随机
  报 `CONNECT tunnel failed, response 502` 或 `TLS handshake timeout`。**必须写重试循环**
  （`for i in $(seq 1 10); do ...; sleep 5; done`），通常 1~3 次内成功。
  另外：`gh api -X DELETE` 超时后可能**已成功执行**（请求发出但响应丢失），
  后续再删会返回 422 `Reference does not exist`——这是「已经删掉了」的信号，不是错误。
- 最终：`gh release create v0.1.0 --target main --title ... --notes-file ...` 发布成功，
  远程 tag → `1b06249`，非草稿非预发布。发布页
  https://github.com/KaneDing1023/enterprise-kb-agent/releases/tag/v0.1.0
